# 现有部署保存与迁移

仓库是从已经运行的重实现整理而来。为避免把某台机器的私有配置保存到 Git，真实地址、代理密码、腾讯云凭据、节点令牌、实际函数 URL、账本和日志都没有提交。

## 现场版本与通用版本的目录差异

已运行的现场版本使用：

```text
服务：cloudproxypool
程序：/opt/cloudproxypool/scf-tunnel
运行配置：/etc/cloudproxypool/tunnel.json
费用账本：/var/lib/cloudproxypool/usage.json
日志：/var/log/cloudproxypool/service.log
健康检查：cloudproxypool-watchdog.timer
```

通用安装脚本改用 `scf-tunnel-proxy` / `scftunnel` 和对应目录。核心隧道协议及预算机制一致，通用代码的默认 `-config` 路径也已改名。

**创建 GitHub 仓库不会自动修改或重新部署现场服务。** 不要直接在原入口上再启动第二个监听相同端口的服务。

## 只保存代码，不迁移服务

保留现场配置和账本即可。仓库中的 `-config` 参数支持现有配置文件格式；将来构建新程序时，可继续沿用原 systemd 服务和显式的 `-config /etc/cloudproxypool/tunnel.json`，而不是强行改目录。

## 确需迁移目录或服务器

1. 备份现有程序、systemd 配置、运行配置、费用账本和部署状态；备份权限 600。
2. 记录当前云端函数名称、URL、节点令牌以及账户/区域信息；不要提交到 Git。
3. 在独立端口验证新程序，使用独立测试账本；不要与运行进程共享账本。
4. 切换时先停原健康检查，再正常停止旧入口，使连接结算并关闭。客户端需要重连。
5. 将账本复制到新服务的数据目录，更新 `ledger_path`，设置新服务用户的所有权。不要把空账本覆盖原账本。
6. 保留代理账号密码、节点令牌和实际节点 URL。私有配置也可以继续沿用旧路径，但应相应调整服务用户权限与 systemd 的 `ReadWritePaths`。
7. 启动新入口，验证认证、真实网站证书、HTTP/SOCKS5 和预期并发后，再停用旧入口的启动项。

如果切换了入口机器，需要更新客户端服务器地址及网络访问控制；不需要代理 CA。

## 已存在的云函数

通用部署工具通过 `scf-tunnel-proxy managed:v1` 标记拥有的函数，故意拒绝覆盖其他标记，包括历史现场函数。历史函数不是“孤立垃圾”，不要因为工具拒绝覆盖就删除它们。

要继续使用现有函数，可保留实际节点清单和令牌，直接运行入口，不必重建云端；要更新历史云函数，应先备份、确认所属和访问路径，再用对应的现场部署流程。需要完整迁移为新的通用部署时，使用新函数名部署并验证，再切换节点清单，最后人工确认是否清理旧资源。

## 文档验证边界

仓库核心协议和稳定性机制来自现场已验证代码，通用部署工具是去掉机器绑定后整理的实现，经过离线单元测试、SDK 请求结构依据及打包预览检查；未在创建本仓库时另开一套收费云环境做完整首次安装。请在自己的账号和目标系统按顺序验收。
